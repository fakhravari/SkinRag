# راهنمای پروژهٔ SkinRag

این برنامهٔ وب فارسی با نام SkinRag برای مرور کاتالوگ و پیشنهاد محصولات پوست، مو، زیبایی و دیگر حوزه‌های ثبت‌شده ساخته شده است. برنامه با ASP.NET Core و .NET 10 ساخته شده، اطلاعات کاتالوگ و موجودی را از SQL Server می‌خواند و برای طبقه‌بندی پیام، استخراج جست‌وجو، ساخت بردار و گاهی نگارش پاسخ از Ollama استفاده می‌کند.

این راهنما ساختار برنامه، آماده‌سازی و اجرای آن، و مسیر کامل یک درخواست را از ارسال پیام تا بازگشت پاسخ توضیح می‌دهد.

## معرفی اجزای برنامه

برنامه از چند جزء تشکیل شده است:

| جزء | کار آن |
| --- | --- |
| برنامهٔ وب | صفحهٔ گفت‌وگو، صفحهٔ مدیریت و APIها را میزبانی می‌کند. |
| پایگاه دادهٔ SQL Server | اطلاعات زندهٔ محصولات، دسته‌بندی‌ها، برندها، ویژگی‌ها، موجودی و قیمت را نگه می‌دارد. |
| سرویس Ollama | مدل‌های محلی را برای کارهای زبانی و ساخت embedding اجرا می‌کند. |
| نمایهٔ دانش | متن و بردار محصولات فعال را برای جست‌وجوی معنایی در حافظه نگه می‌دارد؛ نسخهٔ بردارها در SQL نیز cache می‌شود. |
| ثبت عملکرد | زمان بخش‌های مختلف درخواست و نتیجهٔ آن را در صف پس‌زمینه به جدول گزارش‌ها می‌نویسد. |

برنامه یک وب‌اپلیکیشن واحد است. پوشه‌های Application و Infrastructure بخش‌های مفهومی داخل همین پروژه‌اند و سرویس‌های جداگانه یا پردازه‌های مستقل نیستند. SQL Server و Ollama سرویس‌های بیرونی موردنیاز برنامه‌اند. مسیر مشاوره در برنامه محدودیت ثابت ۱۲ درخواست در دقیقه ندارد؛ تعداد درخواست‌های هم‌زمان در عمل به ظرفیت میزبان، SQL Server و Ollama وابسته است.

## آماده‌سازی و اجرا

### پیش‌نیازها

برای اجرای کامل برنامه این موارد لازم‌اند:

- نصب .NET 10 SDK.
- دسترسی برنامه به SQL Server و پایگاه داده‌ای که جدول‌های موردنیاز برنامه را دارد.
- نصب و اجرای Ollama.
- دریافت مدل‌های تنظیم‌شده در فایل پیکربندی. تنظیم فعلی از مدل‌های زیر استفاده می‌کند:

~~~powershell
ollama pull bge-m3
ollama pull qwen2.5:3b
ollama pull qwen2.5:7b
~~~

نام دقیق مدل گفت‌وگو، نیت، استخراج جست‌وجو و embedding از تنظیمات خوانده می‌شود؛ لزوماً همهٔ این مدل‌ها در هر درخواست استفاده نمی‌شوند.

### آماده‌سازی پایگاه داده

برنامه هنگام اجرا جدول‌های اصلی کاتالوگ را ایجاد یا migrate نمی‌کند. پایگاه داده باید پیش از اجرا دارای ساختار سازگار باشد. فایل‌های موجود در پوشهٔ database شامل نسخهٔ پشتیبان و اسکریپت‌های SQL پروژه‌اند؛ پیش از بازیابی نسخهٔ پشتیبان، نام پایگاه داده و مناسب‌بودن آن برای محیط مقصد را بررسی کنید.

برای ثبت عملکرد مشاوره، جدول dbo.ConsultationPerformanceLogs لازم است. تعریف جدول و نمایهٔ آن در database/scripts.sql آمده است؛ اگر پایگاه دادهٔ مقصد این جدول را ندارد، ساختار جدول را با نسخهٔ برنامه هماهنگ کنید. این جدول از جدول‌های کاتالوگ جداست.

برای پایگاه دادهٔ موجود، مهاجرت‌های افزایشی داخل `database/migrations` را روی همان پایگاه داده اجرا کنید. مهاجرت `20261004_10_AddConsultationPerformanceLogColumns.sql` ستون‌های گزارش را در صورت نبودن اضافه می‌کند و اجرای دوبارهٔ آن بی‌خطر است:

~~~powershell
sqlcmd -S <server> -d <database> -E -b -i database/migrations/20261004_10_AddConsultationPerformanceLogColumns.sql
~~~

ساختار EF Core باید با نام ستون‌های موجود در SQL هماهنگ باشد؛ برای نمونه، دسته‌بندی از `IdParent`، محصول از `IdCategory` و `IdBrand` و پیوندهای محصول از ستون‌های `IdProduct` استفاده می‌کنند. مدل پروفایل کاتالوگ با جدول `CatalogProfiles` و عبارت‌های نگاشت دسته‌بندی با `CatalogPhrases` کار می‌کند. بررسی دیتابیس این تطبیق ستون‌ها و سلامت رابطه‌های کلیدی را کنترل می‌کند.

رشتهٔ اتصال را در SkinRag.Api/appsettings.json یا با متغیر محیطی ConnectionStrings__DefaultConnection تنظیم کنید. اطلاعات محرمانه را در فایل‌های ثبت‌شده در مخزن قرار ندهید.

~~~text
Server=localhost;Database=SkinRagDb;Trusted_Connection=True;TrustServerCertificate=True;
~~~

### اجرای برنامه

از پوشهٔ اصلی مخزن اجرا کنید:

~~~powershell
dotnet run --project SkinRag.Api
~~~

نشانی‌های محلی در خروجی اجرا یا SkinRag.Api/Properties/launchSettings.json دیده می‌شوند. صفحهٔ گفت‌وگو در مسیر /chat و صفحهٔ مدیریت در مسیر /admin است. Swagger در محیط توسعه از مسیر /swagger در دسترس است.

در شروع کار، سرویس پس‌زمینهٔ نمایهٔ دانش محصولات فعال را می‌خواند و snapshot جست‌وجو را می‌سازد. تا آماده‌شدن snapshot، مسیرهایی که به جست‌وجوی معنایی نیاز دارند پاسخ‌گو نیستند؛ وضعیت را از مسیر /api/knowledge/status ببینید. پرسش‌هایی که قبل از بازیابی محصول پاسخ مستقیم می‌گیرند ممکن است به snapshot نیاز نداشته باشند.

## مسیر درخواست مشاوره، گام‌به‌گام

نمونهٔ این مسیر، پیام «برای پوست خشک یک کرم مرطوب‌کنندهٔ ارزان می‌خواهم» است. همهٔ درخواست‌ها الزاماً همهٔ گام‌های زیر را طی نمی‌کنند؛ مسیر به نوع پیام، فیلترهای تشخیص‌داده‌شده و موجودبودن نتیجه بستگی دارد.

### گام ۱: رابط کاربری پیام را می‌فرستد

صفحهٔ گفت‌وگو در فایل SkinRag.Api/wwwroot/assets/chat.js درخواست POST را به مسیر /api/consultation/ask می‌فرستد. بدنه می‌تواند شامل متن پرسش، شناسهٔ مکالمه، چند نوبت اخیر گفت‌وگو، فیلترهای انتخاب‌شده و گزینهٔ نمایش صرفاً بر اساس فیلترها باشد.

درخواست از ConsultationController وارد ConsultationService می‌شود. کنترلر اعتبارسنجی مدل ورودی را انجام می‌دهد و نتیجهٔ سرویس را در قالب ConsultationResponse برمی‌گرداند. مهلت کلی پردازش سمت سرور به‌طور پیش‌فرض ۲۲۰ ثانیه و مهلت انتظار رابط چت ۲۳۰ ثانیه است؛ هر مرحلهٔ Ollama نیز مهلت جداگانه دارد.

### گام ۲: متن نرمال و کنترل می‌شود

در ConsultationService طول پرسش کنترل می‌شود و InputNormalizer شکل‌های متفاوت حروف عربی و فارسی، رقم‌ها، فاصله‌های اضافه و نویسه‌های نامرئی را یکدست می‌کند. سپس InputGuard پیام خالی، بیش از حد بلند، تکرار غیرعادی نویسه‌ها و برخی ورودی‌های هرز را رد می‌کند.

وضعیت مکالمه از ConversationStore خوانده می‌شود. این وضعیت در حافظهٔ همان پردازه نگهداری می‌شود و شامل پرسش‌های اخیر، محصولات قبلی و بودجهٔ پیگیری است؛ تاریخچهٔ کامل مکالمه در پایگاه داده ذخیره نمی‌شود. پیام تکراری نیز ممکن است پیش از جست‌وجو رد شود.

### گام ۳: نیت و موضوع پیام تشخیص داده می‌شود

در مرحلهٔ IntentClassifier مشخص می‌شود پیام درخواست پیشنهاد محصول است، دربارهٔ قیمت یا موجودی یا جزئیات محصول می‌پرسد، مقایسه می‌خواهد، پیگیری مکالمه است، یا به توضیح بیشتری نیاز دارد.

برای الگوهای روشن، از قواعد برنامه استفاده می‌شود؛ برای پیام‌های مبهم‌تر، مدل Intent در Ollama خروجی ساخت‌یافته می‌دهد. خروجی مدل و میزان اطمینان آن بررسی می‌شود. اگر مدل پاسخ معتبر ندهد یا اطمینان کافی نباشد، برنامه با احتیاط مسیر توضیح بیشتر را برمی‌گزیند و پیام نامشخص را به‌طور خودکار به جست‌وجوی محصول تبدیل نمی‌کند.

قواعد ConsultationIntentRules فقط با دیدن یک واژهٔ مربوط به نیاز مراقبتی، پیام را مشاوره حساب نمی‌کنند. پرسش تعریفی مانند «X چیست؟» و اشاره به محصول یا پاسخ قبلی، به مدل یا مسیر روشن‌سازی می‌رسد؛ درخواست روشن برای معرفی محصول می‌تواند مستقیم به جست‌وجوی کاتالوگ برود. این مرزبندی از اشتباه‌گرفتن پرسش اطلاعاتی با درخواست مشاوره جلوگیری می‌کند.

درخواست روشن محصول با ساخت‌های رایج «می‌خواهم/می‌خوام» و نام محصولی مانند کرم یا مرطوب‌کننده، حتی بدون تطبیق با نیاز ثبت‌شده، مستقیم به جست‌وجوی کاتالوگ می‌رود. نیم‌فاصلهٔ فعل خواستن هم نرمال می‌شود.

سلام، گفت‌وگوی کوتاه، موضوع خارج از حوزه و برخی درخواست‌های نیازمند روشن‌سازی می‌توانند همین‌جا پاسخ مستقیم بگیرند. در این مسیرها لزوماً کاتالوگ، SQL یا embedding جست‌وجو نمی‌شود.

### گام ۴: واژگان کاتالوگ خوانده می‌شود

برای درخواست‌های مرتبط با کاتالوگ، برنامه دسته‌بندی‌ها، برندها، پروفایل‌ها، نیازهای مراقبتی، ترکیبات و گزینه‌های رنگ و جلوه را از SQL می‌خواند. این اطلاعات به QueryBuilder داده می‌شود تا عبارت فارسی و فیلترها را به مقادیر معتبر کاتالوگ نگاشت کند.

جدول `CatalogPhrases` منبع یگانه عبارت‌های مشتری برای دسته‌بندی، Concern و پروفایل‌های کاتالوگ است. `CatalogPhraseMatcher` وضعیت نگاشت و تطبیق نرمال‌شده را به‌صورت مشترک برای نیت‌سنجی، فیلترها و گسترش عبارت جست‌وجو اعمال می‌کند. هر ردیف فعال با `MappingStatus=Product` باید دست‌کم یک مقصد رابطه‌ای معتبر داشته باشد و مقصدش به محصول فعال برسد. عبارت‌هایی که فعلاً محصول مرتبط ندارند حذف نمی‌شوند؛ با `MappingStatus=DefinitionOnly` و مقدار `Definition` نگه داشته می‌شوند و در نیت‌سنجی، تطبیق دسته و گسترش جست‌وجو دخالت نمی‌کنند. عبارت‌های مشاوره نیز هنگام مهاجرت در همین جدول با `IdConcern` ادغام می‌شوند.

برای دیتابیس‌های موجود، مهاجرت `database/migrations/20261004_11_UnifyCatalogPhrases.sql` را پس از بازبینی اجرا کنید. این مهاجرت در یک تراکنش اجرا می‌شود، مقصدهای نامعتبر/بدون محصول را به حالت تعریفی می‌برد، متن عبارت‌ها را نگه می‌دارد و در پایان جدول قدیمی `ConsultationPhrases` را پس از انتقال ردیف‌ها حذف می‌کند. اسکریپت کامل ساخت دیتابیس (`database/scripts.sql`) همین مرحله را در انتها دارد.

### گام ۵: برنامهٔ جست‌وجو و فیلترها ساخته می‌شوند

در QueryBuilder یک SearchPlan ساخته می‌شود که عبارت جست‌وجو، حوزه، دسته‌بندی، برند، نوع پوست یا مو، نیاز مراقبتی، بازهٔ قیمت، رنگ، جلوه، اندازه، وضعیت بدون عطر، ترکیبات مستثنا، شناسهٔ محصول و روش موجودی را مشخص می‌کند.

حوزه‌های قابل انتخاب عبارت‌اند از پوست (skin)، مو (hair)، زیبایی (beauty)، بهداشتی و مراقبتی (personal-care)، خوشبوکننده (fragrance)، سلولزی (cellulose)، کالای تبلیغاتی (promotional)، خوراکی (food)، محصولات دیگر (other)، بسته‌های ترکیبی (bundles) و جشنواره‌ها (campaigns).

درخواست‌هایی که دسته یا فیلترشان از متن و قواعد قابل تشخیص است، از مسیر قاعده‌محور استفاده می‌کنند و برای همان استخراج، مدل Query را صدا نمی‌زنند. برای عبارت‌های پیچیده‌تر، مدل Query در Ollama اطلاعات ساخت‌یافتهٔ جست‌وجو را استخراج می‌کند. خروجی آن با واژگان دیتابیس کنترل می‌شود و حوزهٔ قطعی درخواست دوباره روی آن اعمال می‌شود تا مدل نتواند محصول حوزهٔ دیگری وارد جست‌وجو کند.

اگر استخراج مدلی در دسترس نباشد، برنامه تلاش می‌کند با متن خود کاربر، بسط واژگانی و فیلترهای صریح ادامه دهد. اگر اطلاعات متناقض باشد، مثلاً حداقل قیمت از سقف بیشتر باشد، به‌جای جست‌وجو سؤال روشن‌کننده می‌پرسد.

### گام ۶: ابتدا SQL محصولات مجاز را غربال می‌کند

در ProductRepository و CatalogQueryService پرس‌وجوی SQL با شرط‌های SearchPlan ساخته می‌شود. این مرحله ابتدا شناسهٔ محصولاتی را پیدا می‌کند که از فیلترهای اجباری عبور کرده‌اند. شرایط می‌توانند شامل این موارد باشند:

- فعال‌بودن محصول و قرارگرفتن آن در حوزه یا دسته‌بندی انتخاب‌شده.
- برند، نوع پوست، نوع مو و نیاز مراقبتی.
- ثبت قطعی وضعیت بدون عطر و مستثناکردن ترکیبات، در صورت درخواست کاربر.
- موجودی، قیمت، رنگ، جلوه و اندازهٔ variant فعال.

شرط‌های قیمت، موجودی، رنگ، جلوه و اندازه روی یک variant واحد اعمال می‌شوند تا قیمت یک اندازه با موجودی اندازهٔ دیگری ترکیب نشود. اگر محصول variant نداشته باشد، قواعد جایگزین مبتنی بر اطلاعات خود محصول اجرا می‌شود؛ برای رنگ، جلوه و اندازه در این حالت تطبیقی انجام نمی‌شود.

### گام ۷: اگر SQL نتیجه‌ای نداشته باشد، جست‌وجو زود تمام می‌شود

اگر SQL هیچ شناسهٔ واجد شرایطی برنگرداند، ProductRetriever فوراً نتیجهٔ خالی می‌دهد. در این حالت embedding پرسش ساخته نمی‌شود و جست‌وجوی برداری هم اجرا نمی‌شود؛ این علت رایج پاسخ بسیار سریع «محصول مرتبطی مطابق فیلترها و اطلاعات فعلی پیدا نشد» است.

پس این پیام الزاماً به معنی اجراشدن جست‌وجوی معنایی نیست. ممکن است کاتالوگ در SQL بررسی شده باشد، اما هیچ محصول فعالی با همهٔ فیلترهای هم‌زمان سازگار نباشد؛ مثلاً دسته‌بندی، حوزه، موجودی یا بازهٔ قیمت نتیجه را صفر کند.

### گام ۸: نامزدهای SQL با نمایهٔ دانش رتبه‌بندی می‌شوند

وقتی SQL شناسه‌های مجاز برگرداند، برنامه آن‌ها را با snapshot حافظه تطبیق می‌دهد. برای درخواست دارای شناسهٔ روشن محصول، بارگذاری مستقیم انجام می‌شود و جست‌وجوی معنایی لازم نیست.

در جست‌وجوی متنی عادی، Ollama برای عبارت SearchPlan بردار embedding می‌سازد. برنامه فقط اسناد محصولی را بررسی می‌کند که شناسه‌شان از فیلتر SQL عبور کرده است؛ بنابراین بردار معنایی اجازه ندارد قید حوزه یا فیلترهای دیتابیس را دور بزند.

برای هر نامزد، شباهت کسینوسی بردار پرسش و بردار محصول محاسبه می‌شود. سپس امتیاز ترکیبی با تطبیق واژه‌ها محاسبه، نامزدهای زیر حداقل شباهت حذف و حداکثر تعداد تعیین‌شده نگه داشته می‌شود. مقدار پیش‌فرض حداقل شباهت ۰٫۲۰ و تعداد معمول نتایج نهایی ۵ است.

### گام ۹: جزئیات، قیمت و موجودی دوباره از SQL تازه می‌شوند

بردار و متن نمایه برای بازیابی سریع در حافظه هستند، اما قیمت و موجودی مرجع نهایی‌شان SQL است. شناسه‌های رتبه‌گرفته دوباره با شرط‌های جاری از پایگاه داده بارگذاری می‌شوند؛ variant فعال و واجد شرایط نیز همراه محصول برگردانده می‌شود.

در نتیجه، موجودی یا قیمت تغییرکرده از دادهٔ قدیمی نمایهٔ معنایی خوانده نمی‌شود. اگر هیچ candidate از SQL با snapshot یا بارگذاری نهایی تطبیق نکند، مسیر نتیجهٔ خالی یا خطای وضعیت نمایه ثبت می‌کند.

### گام ۱۰: پاسخ مستقیم یا پاسخ مدل انتخاب می‌شود

پرسش قیمت، موجودی و جزئیات محصول معمولاً با داده‌های تازهٔ کاتالوگ قالب‌بندی می‌شود و نیازی به تولید پاسخ آزاد توسط مدل ندارد. درخواست‌های صریح و قاعده‌محور محصول و انتخاب صرفاً با فیلترها نیز از پاسخ grounded کاتالوگ استفاده می‌کنند.

برای درخواست‌های دیگری که نیاز به توضیح مشاوره‌ای دارند، مدل Consultation در Ollama پاسخ ساخت‌یافته می‌سازد. ورودی مدل فقط شامل پرسش و اطلاعات چند محصول بازیابی‌شده است؛ مدل منبع مستقل اطلاعات کاتالوگ نیست.

### گام ۱۱: پاسخ و محصولات اعتبارسنجی می‌شوند

در RecommendationValidator شناسهٔ هر پیشنهاد بررسی می‌شود در میان محصولات مجاز همین درخواست باشد، تکراری نباشد، دلیل پیشنهاد از گزینه‌های مجاز بیاید و محصول طبق اطلاعات تازهٔ SQL هنوز موجود و سازگار با فیلترها باشد.

اگر مدل خراب یا غیرقابل استفاده پاسخ دهد، برنامه از پاسخ مبتنی بر اطلاعات کاتالوگ استفاده می‌کند و آن را نیز اعتبارسنجی می‌کند. اگر اعتبارسنجی موفق نشود یا دادهٔ تازه با نتیجهٔ قبلی سازگار نباشد، محصول نامعتبر به کاربر نمایش داده نمی‌شود.

### گام ۱۲: مکالمه و زمان‌بندی ثبت می‌شوند

اگر محصولی با موفقیت برگردد، ConversationStore شناسهٔ محصولات و زمینهٔ لازم برای پیگیری‌هایی مانند «قیمتش چنده؟» یا «ارزان‌ترش را می‌خواهم» را در حافظه نگه می‌دارد.

در پایان هر درخواست، ConsultationService زمان کل، مرحله‌ها، نیت، منبع ساخت query، روش بازیابی، تعداد محصول، مدل‌های فراخوانی‌شده و نتیجه را در صف ثبت عملکرد می‌گذارد. سرویس پس‌زمینه رکوردها را دسته‌ای در SQL ذخیره می‌کند. ثبت زمان‌ها بعد از آماده‌شدن پاسخ انجام می‌شود و در مسیر پاسخ‌دهی به‌صورت نوشتن مستقیم و هم‌زمان روی دیتابیس اجرا نمی‌شود.

### گام ۱۳: پاسخ به رابط کاربری برمی‌گردد

در ConsultationController شیء ConsultationResponse با متن پاسخ، محصولات، قیمت و variantهای مجاز، روش بازیابی، تعداد نامزدهای SQL، زمان snapshot، نیت و حالت پاسخ برمی‌گرداند. رابط کاربری متن، کارت‌های محصول و در صورت وجود سؤال روشن‌کننده را نمایش می‌دهد.

## مسیر جست‌وجوی کاتالوگ

جست‌وجوی صفحهٔ کاتالوگ با درخواست‌های مشاوره یکی نیست. صفحهٔ کاتالوگ مستقیماً endpointهای CatalogController را فراخوانی می‌کند. جست‌وجو و فیلترهای این صفحه در SQL اجرا می‌شوند و نتایج صفحه‌بندی‌شده برمی‌گردند؛ این مسیر برای هر جست‌وجو از مدل زبانی یا embedding استفاده نمی‌کند.

مسیر /api/catalog/filters فهرست حوزه‌ها، دسته‌ها، برندها، پروفایل‌ها، نیازها، ترکیبات، رنگ‌ها و جلوه‌های قابل انتخاب را می‌دهد. مسیر /api/catalog/stats تعداد محصولات، variantها و دسته‌ها را گزارش می‌کند.

مقایسهٔ slugها و مقادیر متنی فیلتر در سرویس کاتالوگ نسبت به بزرگی و کوچکی حروف حساس نیست؛ ارسال یک مقدار با دو شکل حروف، نتیجه را دوبار نمی‌شمارد. هنگام ترکیب دسته با حوزه نیز دسته‌بندی باید با همان حوزه سازگار باشد.

## فیلترهای صفحه گفت‌وگو

فیلترهای این صفحه اختیاری‌اند. کاربر می‌تواند بدون فیلتر پیام بنویسد یا متن را خالی بگذارد و فقط با فیلترها جست‌وجو کند. فرستادن متن پرسش، فیلترهای انتخاب‌شده را پاک می‌کند تا دو حالت با هم ترکیب نشوند.

در فهرست چندانتخابی، یک انتخاب نام خودش و چند انتخاب فقط تعدادشان را در نشان کنار فلش نشان می‌دهند. پس از جست‌وجوی فیلترمحور، گزینه‌های انتخاب‌شده به‌صورت برچسب‌های هم‌رنگ رابط، زیر پیام کاربر می‌آیند؛ خلاصهٔ تکراری بالای گفت‌وگو نمایش داده نمی‌شود. فیلتر حذف ترکیبات صرفاً نتیجه را بر اساس اطلاعات ثبت‌شده محدود می‌کند و تضمین پزشکی یا ایمنی در برابر حساسیت نیست.

## نمایهٔ دانش و embeddingها

نمایهٔ دانش در شروع برنامه و سپس در فاصله‌های دوره‌ای توسط KnowledgeIndexBackgroundService بازسازی می‌شود. فاصلهٔ پیش‌فرض ۳۰۰ ثانیه است. KnowledgeIndexService محصولات فعال را از SQL می‌خواند، متن جست‌وجو را از نام، حوزه، دسته، برند، ویژگی‌ها، نیازها، واژه‌های جست‌وجو، ترکیبات، توضیحات، روش مصرف و variantها می‌سازد و برای آن embedding می‌گیرد.

بردارها در جدول ProductEmbeddings با مدل، ابعاد، هش محتوای منبع و زمان به‌روزرسانی cache می‌شوند. اگر هش متن، نسخهٔ embedding یا پیشوند متن تغییر نکرده باشد، بردار ذخیره‌شده دوباره استفاده می‌شود. snapshot آمادهٔ جست‌وجو در حافظهٔ پردازه قرار می‌گیرد؛ قیمت و موجودی در این snapshot مرجع نهایی نیستند.

تغییرات دیتابیس در snapshot ممکن است تا اجرای نوبت بعدی بازسازی دیده نشوند. وضعیت بازسازی، آخرین زمان به‌روزرسانی، تعداد cache و خطا از /api/knowledge/status قابل مشاهده است. برای شروع بازسازی دستی از POST /api/knowledge/rebuild استفاده می‌شود. گزینهٔ force=true باعث می‌شود embeddingها دوباره ساخته شوند؛ این کار برای تغییر معمول قیمت یا موجودی لازم نیست.

اگر مدل embedding یا ابعاد بردار عوض شود، نسخهٔ embedding را هم به‌روز کنید و بازسازی کامل انجام دهید. مقایسهٔ بردارهای مدل‌های ناسازگار معتبر نیست.

## پاسخ سریع و پاسخ مدل

همهٔ پیام‌ها الزاماً مدل گفت‌وگو را اجرا نمی‌کنند:

| نوع درخواست | مسیر معمول |
| --- | --- |
| سلام، احوال‌پرسی یا درخواست خارج از حوزه | پاسخ مستقیم پس از تشخیص نیت؛ جست‌وجوی محصول لازم نیست. |
| فیلتر صریح یا دستهٔ قابل شناسایی | ساخت SearchPlan قاعده‌محور؛ ممکن است استخراج مدل Query حذف شود. |
| پرسش قیمت، موجودی یا جزئیات محصول | بازیابی و قالب‌بندی از کاتالوگ؛ معمولاً تولید آزاد مدل پاسخ لازم نیست. |
| درخواست مشاورهٔ متنی پیچیده | تشخیص نیت، ساخت query، فیلتر SQL، بازیابی برداری و در صورت نیاز تولید و اعتبارسنجی پاسخ. |
| صفرشدن فهرست SQL | پایان فوری با نتیجهٔ خالی؛ embedding و مدل پاسخ فراخوانی نمی‌شوند. |
| پاسخ نامعتبر یا دردسترس‌نبودن مدل پاسخ | استفاده از پاسخ grounded کاتالوگ، مشروط به موفقیت اعتبارسنجی. |

برای عیب‌یابی، «زمان کم» به‌تنهایی نشان نمی‌دهد چه مسیری اجرا شده است. QuerySource، RetrievalMethod، SqlFilterMs، EmbeddingMs، AnswerGenerationMs، ResponseMode و ProductCount را کنار هم بررسی کنید.

## وقتی محصولی پیدا نمی‌شود

پیام «محصول مرتبطی مطابق فیلترها و اطلاعات فعلی پیدا نشد» وقتی برمی‌گردد که بازیابی نهایی محصولی نداشته باشد. علت‌های متداول عبارت‌اند از:

- فیلتر حوزه یا دسته با دسته‌بندی ثبت‌شدهٔ محصول سازگار نیست.
- محصول غیرفعال است یا به‌علت موجودی از جست‌وجو حذف شده است.
- چند فیلتر هم‌زمان برقرار نیستند؛ مثلاً بازهٔ قیمت و اندازهٔ انتخابی روی یک variant واحد وجود ندارد.
- عبارت جست‌وجو با نام و اطلاعات توصیفی محصولات موجود شباهت کافی ندارد.
- snapshot محصول به‌روز نیست یا محصول واجد شرایط SQL در snapshot فعلی نیست.

در لاگ، اگر RetrievalMethod برابر sql-filters و EmbeddingMs خالی باشد، SQL شناسهٔ واجد شرایطی پیدا نکرده و بازیابی برداری آغاز نشده است. اگر EmbeddingMs مقدار داشته باشد، مرحلهٔ برداری اجرا شده است؛ در این حالت SearchQuery، QuerySource، ProductCount و زمان بارگذاری محصول را هم بررسی کنید. مقدار EligibleProducts تعداد شناسه‌های عبورکرده از SQL را نشان می‌دهد و ProductCount تعداد محصولاتی است که در پاسخ به کاربر برگشته‌اند؛ این دو الزاماً برابر نیستند.

## پایگاه داده و ثبت عملکرد

جدول‌های اصلی برنامه این موجودیت‌ها را نگه می‌دارند:

| گروه داده | جدول‌ها و ارتباط |
| --- | --- |
| محصولات | Products شامل اطلاعات پایه، توضیحات، قیمت پایه و وضعیت فعال‌بودن است. |
| گزینه‌های قابل‌فروش | ProductVariants قیمت، موجودی، رنگ، جلوه و اندازهٔ هر variant را نگه می‌دارد. |
| دسته‌بندی و برند | Categories و Brands از طریق شناسهٔ خارجی به Products متصل‌اند. دسته‌بندی دارای حوزه و والد است. |
| ویژگی‌های محصول | CatalogProfiles، Concerns و Ingredients با جدول‌های ProductProfiles، ProductConcerns و ProductIngredients به محصولات متصل‌اند. |
| عبارت‌های مشتری | CatalogPhrases عبارت را با FK به دسته، Concern یا پروفایل وصل می‌کند؛ عبارت بدون محصول با Definition و MappingStatus=DefinitionOnly حفظ می‌شود و در مسیریابی/جست‌وجوی محصول وارد نمی‌شود. |
| بردار جست‌وجو | ProductEmbeddings بردار cacheشدهٔ هر محصول را برای هر مدل embedding نگه می‌دارد. |
| گزارش عملکرد | ConsultationPerformanceLogs زمان و نتیجهٔ پردازش درخواست‌های مشاوره را ذخیره می‌کند. |

گزارش عملکرد درخواست‌هایی را ثبت می‌کند که از اعتبارسنجی اولیهٔ کنترلر عبور کرده و وارد سرویس endpoint مشاوره (`POST /api/consultation/ask`) می‌شوند؛ درخواست‌های صفحهٔ کاتالوگ، صفحه‌های وب و سایر endpointها در این جدول ثبت نمی‌شوند. هر رکورد شامل شناسه و زمان آغاز و پایان محلی، TotalMs، زمان نیت، خواندن واژگان، ساخت query، فیلتر SQL، embedding، بارگذاری محصول، تولید پاسخ و اعتبارسنجی است. همچنین Intent، QuerySource، SearchQuery، RetrievalMethod، ResponseMode، ProductCount، Outcome، ErrorType و ModelCallsJson را نگه می‌دارد. مسیر، روش HTTP، شناسهٔ trace، IP، User-Agent، نام مرورگر و سیستم‌عامل درخواست نیز ذخیره می‌شوند. متن SearchQuery با تنظیم `Telemetry:LogSearchQuery` کنترل می‌شود و مقدار پیش‌فرض آن `true` است؛ برای ننوشتن متن جست‌وجو این گزینه را خاموش کنید.

ModelCallsJson جزئیات زمان هر فراخوانی مدل مانند مرحله، نام مدل، توکن‌ها و زمان بارگذاری و تولید را نگه می‌دارد.

صف ثبت عملکرد در حافظه است و پس‌زمینه رکوردها را به‌صورت دسته‌های حداکثر ۱۰۰تایی ذخیره می‌کند. ظرفیت صف ۵۰۰۰ رکورد است. در صورت خطای SQL، ذخیرهٔ هر دسته تا سه بار با مکث دوباره امتحان می‌شود و خطا در گزارش برنامه ثبت می‌شود؛ اگر هر سه تلاش شکست بخورد، صف پر شود یا برنامه ناگهانی خاموش شود، رکوردهای ذخیره‌نشده ممکن است از دست بروند. خود پاسخ مشاوره برای ثبت گزارش منتظر نوشتن هم‌زمان یک رکورد در جدول نمی‌ماند.

صفحهٔ `/admin` و endpoint بازسازی `POST /api/knowledge/rebuild` در نسخهٔ فعلی احراز هویت مدیریتی ندارند. آن‌ها را فقط در شبکه یا محیطی در دسترس قرار دهید که دسترسی به آن محدود شده است؛ بازسازی کامل embedding می‌تواند زمان‌بر و پرهزینه باشد.

زمان ستون‌های گزارش با ساعت محلی ماشینی که برنامه روی آن اجرا می‌شود ثبت می‌شود. در محیطی که چند میزبان یا منطقهٔ زمانی متفاوت دارد، تفسیر زمان‌ها باید با منطقهٔ زمانی همان میزبان انجام شود.

| حداقل اطمینان مدل نیت؛ پیش‌فرض ۰٫۶۵ | Consultation:MinimumIntentConfidence |
| سقف توکن خروجی مرحلهٔ نیت | Consultation:IntentMaxTokens |
| سقف توکن خروجی مرحلهٔ query | Consultation:QueryMaxTokens |
| سقف توکن خروجی پاسخ | Consultation:AnswerMaxTokens |
| تعداد نتیجه‌های بازیابی؛ پیش‌فرض ۵ | Rag:TopK |
| حداقل شباهت برداری؛ پیش‌فرض ۰٫۲۰ | Rag:MinimumSimilarity |
| تعداد متن در هر دستهٔ embedding هنگام بازسازی؛ پیش‌فرض ۱۶ | Rag:EmbeddingBatchSize |
| پیشوند متن محصول و عبارت کاربر برای مدل embedding | Rag:DocumentPrefix و Rag:QueryPrefix |
| نسخهٔ محتوای embedding برای تشخیص cache قدیمی | Rag:EmbeddingVersion |
| فاصلهٔ بازسازی دوره‌ای نمایه؛ پیش‌فرض ۳۰۰ ثانیه | Rag:RefreshIntervalSeconds |
| فعال‌کردن ذخیرهٔ SearchQuery در گزارش؛ پیش‌فرض true | Telemetry:LogSearchQuery |

مدل embedding با مدل گفت‌وگو کار متفاوتی دارد. تغییر مدل گفت‌وگو بر سرعت و کیفیت نگارش پاسخ اثر می‌گذارد. تغییر مدل embedding یا نسخهٔ محتوای بردار مستلزم بازسازی نمایه است.

## ساختار پوشه‌ها

کل سامانه در همان پروژه و اسمبلی واحد `SkinRag.Api` باقی مانده است. لایه‌ها با پوشه و namespace جدا شده‌اند و پروژهٔ جداگانه‌ای اضافه نشده است.

| لایه | مسئولیت | مسیر |
| --- | --- | --- |
| دامنه | موجودیت‌های کاتالوگ و قواعد مستقل از وب و پایگاه داده | `SkinRag.Api/Domain/Catalog` |
| کاربرد | جریان مشاوره، نیت، جست‌وجو، اعتبارسنجی و قراردادهای ورودی و خروجی | `SkinRag.Api/Application` |
| قراردادهای کاتالوگ | فیلترها، درخواست جست‌وجو، مشخصات محصول و گزینه‌های فیلتر | `SkinRag.Api/Application/Contracts/Catalog` |
| قراردادهای مشاوره | درخواست و پاسخ مکالمه | `SkinRag.Api/Application/Contracts/Consultation` |
| مرزهای کاربرد | رابط مخزن، مدل زبانی، نمایهٔ دانش، کاتالوگ و ثبت عملکرد | `SkinRag.Api/Application/Abstractions` |
| زیرساخت | EF Core، `SkinRagDbContext`، مخزن SQL و موجودیت‌های ذخیره‌سازی | `SkinRag.Api/Infrastructure/Persistence` |
| خواندن کاتالوگ | فیلتر محصولات، صفحه‌بندی، نگاشت خروجی و آمار | `SkinRag.Api/Infrastructure/Catalog` |
| اتصال مدل | ارتباط HTTP با Ollama | `SkinRag.Api/Infrastructure/Integrations/Ollama` |
| نمایهٔ دانش | ذخیرهٔ embedding، بازسازی نمایه و کار پس‌زمینه | `SkinRag.Api/Infrastructure/Knowledge` |
| پایش | صف و ذخیرهٔ زمان‌بندی درخواست‌ها | `SkinRag.Api/Infrastructure/Telemetry` |
| ارائه | کنترلرها و middlewareهای HTTP | `SkinRag.Api/Presentation` |
| ترکیب برنامه | ثبت وابستگی‌ها و پیکربندی pipeline در نقطهٔ شروع | `SkinRag.Api/Hosting` و `SkinRag.Api/Program.cs` |
| رابط وب | صفحه‌های Razor، فایل‌های ایستا و قلم‌ها؛ در ریشه می‌مانند تا قراردادهای پیش‌فرض ASP.NET حفظ شوند | `SkinRag.Api/Views` و `SkinRag.Api/wwwroot` |
| بررسی‌ها و داده | بررسی‌های مستقل نیت‌سنجی و کاتالوگ/دیتابیس، به‌همراه اسکریپت‌های SQL | `tests/SkinRag.IntentRoutingChecks`، `tests/SkinRag.CatalogDbChecks` و `database` |

وابستگی در سطح namespace از ارائه به کاربرد و از زیرساخت به کاربرد و دامنه حرکت می‌کند. کاربرد با زیرساخت از طریق interfaceهای تعریف‌شده در `Application/Abstractions` ارتباط می‌گیرد؛ ثبت پیاده‌سازی‌ها در نقطهٔ ترکیب برنامه انجام می‌شود.

## اجرای بررسی‌های پروژه

بررسی‌های نیت‌سنجی مستقل از سرویس‌های بیرونی‌اند:

~~~powershell
dotnet run --project tests/SkinRag.IntentRoutingChecks
~~~

بررسی‌های کاتالوگ و دیتابیس به SQL Server تنظیم‌شده در `ConnectionStrings:DefaultConnection` وصل می‌شوند و فقط queryهای خواندنی اجرا می‌کنند:

~~~powershell
dotnet run --project tests/SkinRag.CatalogDbChecks
~~~

این بررسی، وجود ستون‌های مورد انتظار EF Core در SQL، فعال و معتبر بودن کلیدهای خارجی، پیوندهای بدون رکورد یتیم، یکتایی عبارت‌های کاتالوگ، معتبر بودن بردارهای embedding و رفتار جست‌وجو و فیلترهای API را ارزیابی می‌کند؛ نام گزینه‌ها با شکل‌های مختلف حروف نیز بررسی می‌شود. این برنامهٔ بررسی، دادهٔ دیتابیس را تغییر نمی‌دهد.

## عیب‌یابی

| نشانه | چه چیزی را بررسی کنید |
| --- | --- |
| وضعیت دانش آماده نیست | اتصال SQL و Ollama را بررسی کنید و GET /api/knowledge/status را بخوانید. |
| پاسخ «محصولی پیدا نشد» خیلی سریع برگشت | RetrievalMethod، EligibleProducts، ProductCount، SqlFilterMs و خالی‌بودن EmbeddingMs را بررسی کنید؛ ممکن است SQL نتیجه را صفر کرده باشد. |
| پاسخ با تأخیر زیاد می‌رسد | TotalMs را با IntentMs، QueryBuildMs، EmbeddingMs و AnswerGenerationMs مقایسه کنید؛ ModelCallsJson جزئیات هر فراخوانی Ollama را دارد. |
| تغییر نام یا توضیح محصول در جست‌وجوی معنایی دیده نمی‌شود | بازسازی دوره‌ای یا POST /api/knowledge/rebuild را بررسی کنید؛ اما قیمت و موجودی هنگام جست‌وجو از SQL زنده بارگذاری می‌شوند. |
| موجودی یا قیمت variant درست نیست | وضعیت فعال‌بودن variant و قیمت و موجودی همان variant در SQL را بررسی کنید. |
| خطای مدل یا خروجی نامعتبر رخ می‌دهد | گزارش برنامه و ModelCallsJson را بخوانید؛ برنامه در بعضی مرحله‌ها پاسخ کاتالوگ را به‌عنوان جایگزین اعتبارسنجی می‌کند. |
| گزارش درخواست مشاوره ثبت نشده است | بررسی کنید درخواست از اعتبارسنجی اولیه عبور کرده و به `POST /api/consultation/ask` رسیده باشد؛ سایر endpointها در این جدول ثبت نمی‌شوند. وجود ستون‌های `QuerySource`، `ModelCallsJson` و `SearchQuery` در `dbo.ConsultationPerformanceLogs` را بررسی و در صورت نیاز مهاجرت `20261004_10_AddConsultationPerformanceLogColumns.sql` را اجرا کنید. خطاهای `ConsultationPerformanceQueue` در گزارش برنامه ثبت می‌شوند و ذخیره پس از خطای SQL تا سه بار دوباره امتحان می‌شود. |

برای بررسی یک درخواست مشخص، ابتدا همان ردیف ConsultationPerformanceLogs را با شناسهٔ درخواست پیدا کنید. سپس SearchQuery و QuerySource را برای فهم عبارت و منشأ طرح جست‌وجو بخوانید؛ Intent و RetrievalMethod نوع مسیر را نشان می‌دهند؛ زمان‌های هر مرحله و ModelCallsJson محل صرف زمان در SQL یا Ollama را مشخص می‌کنند.
