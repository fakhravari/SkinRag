# راهنمای پروژهٔ <bdi dir="ltr">SkinRag</bdi>؛ کاتالوگ و مشاور محصولات پوست، مو و زیبایی

این پروژه با نام SkinRag یک برنامهٔ وب برای نمایش کاتالوگ محصولات مراقبت از پوست، مو و زیبایی و پیشنهاد محصول در گفت‌وگوی فارسی است. برنامه با **ASP.NET Core و .NET 10** ساخته شده، داده‌های کاتالوگ را از **SQL Server** می‌خواند و برای بردارسازی و تولید پاسخ از **Ollama** استفاده می‌کند. رابط چت و پنل مدیریت با Razor، JavaScript و CSS پیاده‌سازی شده‌اند.

## معرفی کوتاه

کاربر می‌تواند در صفحهٔ کاتالوگ محصولات را جست‌وجو و فیلتر کند یا در صفحهٔ چت با زبان طبیعی درخواست بدهد؛ برای نمونه، نوع محصول، نوع پوست یا مو، دغدغه و سقف قیمت را در متن بگوید. برنامه متن را تحلیل می‌کند، محصولات سازگار را از پایگاه داده پیدا می‌کند، آن‌ها را با جست‌وجوی معنایی رتبه‌بندی می‌کند و پاسخ را همراه با اطلاعات ساخت‌یافتهٔ محصول برمی‌گرداند.

برنامه یک وب‌اپلیکیشن واحد است. پوشه‌های `Application` و `Infrastructure` مرزهای مفهومی داخل همان پروژه‌اند و سرویس‌های مستقلی نیستند. کاتالوگ و بردارهای محصولات در SQL Server قرار دارند؛ snapshot بردارهای لازم برای جست‌وجو هنگام اجرا در حافظه نگه داشته می‌شود.

## شروع از صفر تا صد

### پیش‌نیازها

برای اجرای کامل برنامه این موارد لازم‌اند:

- نصب **.NET 10 SDK** برای ساخت و اجرای برنامه.
- دسترسی به یک **SQL Server** و پایگاه داده‌ای با ساختار سازگار با مدل فعلی برنامه.
- نصب و اجرای **Ollama** برای مدل‌های گفتگو و embedding.
- دریافت مدل‌های مورد استفادهٔ تنظیمات فعلی:

<div dir="ltr">

```powershell
ollama pull nomic-embed-text
ollama pull qwen2.5:3b
ollama pull qwen2.5:7b
```

</div>

### آماده‌سازی پایگاه داده

برنامه هنگام اجرا جدول‌های اصلی کاتالوگ را ایجاد یا مهاجرت نمی‌دهد؛ ساختار پایگاه داده باید پیش از اجرای برنامه آماده باشد. فایل پشتیبان کاتالوگ در `database/SkinRagDb.bak` قرار دارد. آن را فقط در محیطی بازیابی کنید که قصد استفاده از همان داده را دارید و نام پایگاه داده و سازگاری ساختار را بررسی کنید. در مخزن، اسکریپت عمومی نصب یا seed کاتالوگ وجود ندارد.

برای ثبت زمان درخواست‌های مشاوره، اسکریپت `database/consultation-performance.sql` جدول مستقل `dbo.ConsultationPerformanceLogs` را ایجاد می‌کند. این جدول از جدول‌های کاتالوگ جداست. در محیط توسعهٔ فعلی، جدول در `SkinRagDb` ایجاد شده است؛ برای محیط دیگری، اسکریپت را روی پایگاه دادهٔ مقصد اجرا کنید.

### تنظیم اتصال و اجرای برنامه

رشتهٔ اتصال را در `SkinRag.Api/appsettings.json` یا از طریق متغیر محیطی `ConnectionStrings__DefaultConnection` تنظیم کنید. برای نمونه، شکل کلی رشتهٔ اتصال در ویندوز چنین است:

<div dir="ltr">

```text
Server=localhost;Database=SkinRagDb;Trusted_Connection=True;TrustServerCertificate=True;
```

</div>

در محیط‌های دیگر، روش احراز هویت متناسب با SQL Server خود را جایگزین کنید. اطلاعات محرمانه را در فایل‌های ردیابی‌شدهٔ مخزن قرار ندهید.

ابتدا مطمئن شوید SQL Server و Ollama در دسترس‌اند، سپس از پوشهٔ اصلی مخزن اجرا کنید:

<div dir="ltr">

```powershell
dotnet run --project SkinRag.Api
```

</div>

نشانی محلی برنامه در خروجی اجرا یا `SkinRag.Api/Properties/launchSettings.json` نمایش داده می‌شود. صفحهٔ اصلی به صفحهٔ چت هدایت می‌شود. مسیرهای اصلی وب عبارت‌اند از `/chat` و `/admin`؛ مستندات Swagger در محیط Development از `/swagger` قابل دسترسی است.

بعد از شروع برنامه، سرویس پس‌زمینه فهرست محصولات فعال را بررسی می‌کند و snapshot دانش را می‌سازد یا به‌روز می‌کند. برای پاسخ‌گویی معنایی، تا آماده‌شدن snapshot باید اتصال دیتابیس برقرار و مدل embedding در دسترس باشد. وضعیت آماده‌بودن را از پنل مدیریت یا مسیرهای سلامت بررسی کنید.

<h2 dir="rtl" style="direction: rtl; text-align: right;">از فرستادن پرسش تا دریافت پاسخ</h2>

وقتی کاربر پیامی مانند «برای پوست خشک یک کرم مرطوب‌کنندهٔ ارزان می‌خواهم» می‌فرستد، مراحل زیر اجرا می‌شوند:

۱. رابط چت درخواست را به `POST /api/consultation/ask` می‌فرستد. پیام، فیلترهای انتخابی و در صورت وجود شناسهٔ مکالمه به API می‌رسند.

۲. کنترلر `ConsultationController` ورودی HTTP را به `ConsultationService` می‌سپارد. طول پیام و ورودی‌های نامعتبر بررسی می‌شوند؛ حداکثر طول پرسش ۲۰۰۰ نویسه است.

۳. دسته‌بند نیت، یعنی `IntentClassifier`، تشخیص می‌دهد کاربر چه می‌خواهد: پیشنهاد محصول، پرسش دربارهٔ قیمت یا موجودی، جزئیات، مقایسه، پیگیری گفتگو یا موضوعی دیگر. قواعد مشخص بعضی پیام‌های رایج را بدون فراخوانی مدل تشخیص می‌دهند؛ در پیام‌های مبهم از مدل intent کمک گرفته می‌شود.

۴. سرویس کاتالوگ و مخزن محصولات، یعنی `CatalogService` و `ProductRepository`، اطلاعات واژگان کاتالوگ را می‌خوانند تا دسته‌ها، برندها، پروفایل‌های پوست و مو، دغدغه‌ها و ترکیبات معتبر در دسترس باشند.

۵. سازندهٔ پرس‌وجو، یعنی `QueryBuilder`، متن و زمینهٔ گفتگو را به `SearchPlan` تبدیل می‌کند. این برنامه شامل عبارت جست‌وجو و فیلترهایی مانند حوزه، دسته، نوع پوست یا مو، بودجه و ترکیبات ممنوع است. برای برخی صورت‌های رایج فارسی، از جمله درخواست کرم مرطوب‌کننده برای پوست خشک، قاعدهٔ مشخص وجود دارد و مدل ساخت query فراخوانی نمی‌شود.

۶. بازیاب محصولات، یعنی `ProductRetriever`، ابتدا فیلترهای قطعی را در SQL اعمال می‌کند. سپس، اگر محصول مشخصی با شناسه درخواست نشده باشد، متن جست‌وجو را با `nomic-embed-text` به بردار تبدیل می‌کند و شباهت آن را با بردار محصولات آماده‌شده می‌سنجد. رتبه‌بندی ترکیبی از شباهت برداری و هم‌پوشانی واژه‌هاست.

۷. قیمت، موجودی و جزئیات محصولات منتخب دوباره از SQL خوانده می‌شوند تا پاسخ بر اطلاعات جاری کاتالوگ تکیه کند. `RecommendationValidator` شناسه و دلیل پیشنهاد را با محصولات مجاز و فیلترهای درخواست تطبیق می‌دهد.

۸. برای پیشنهاد معمول، مدل مشاوره پاسخ ساخت‌یافته تولید می‌کند. برنامه پاسخ را اعتبارسنجی می‌کند و در صورت نامعتبر بودن پاسخ مدل، تا حد امکان از پاسخ مبتنی بر اطلاعات کاتالوگ استفاده می‌کند. پاسخ نهایی شامل متن و محصولات ساخت‌یافته است.

مراحل بالا همیشه همگی اجرا نمی‌شوند. برای پرسش‌های مستقیم دربارهٔ قیمت، موجودی یا جزئیات، پاسخ می‌تواند از کاتالوگ ساخته شود و مرحلهٔ تولید متن با مدل انجام نشود. درخواست فیلترهای مشخص نیز ممکن است بعضی مراحل تحلیل را رد کند.

## جست‌وجوی معنایی و ساخت دانش

جست‌وجوی معنایی به بردارهای هر محصول نیاز دارد. `KnowledgeIndexWorker` هنگام شروع برنامه و سپس با فاصلهٔ تعیین‌شده در `Rag:RefreshIntervalSeconds` بازسازی را بررسی می‌کند. `KnowledgeIndexService` برای هر محصول فعال یک متن از نام، برند، دسته، نوع پوست و مو، دغدغه‌ها، کلیدواژه‌ها، ترکیبات، توضیحات، هشدارها، روش مصرف و گونه‌های فعال محصول می‌سازد.

این متن با پیشوند `Rag:DocumentPrefix` و مدل `Ollama:EmbeddingModel` به embedding تبدیل می‌شود. بردار و فرادادهٔ آن در جدول `ProductEmbeddings` ذخیره می‌شوند. هش محتوا مشخص می‌کند آیا بردار قبلی هنوز معتبر است؛ بنابراین بازسازی معمول فقط محصولات تغییرکرده یا محصولات فاقد بردار معتبر را دوباره پردازش می‌کند.

بازسازی معمول از کش استفاده می‌کند. گزینهٔ اجباری `force=true` کش را نادیده می‌گیرد و همهٔ محصولات فعال را دوباره بردارسازی می‌کند. درخواست بازسازی از `POST /api/knowledge/rebuild?force=true` انجام می‌شود. اجرای بازسازی ممکن است زمان‌بر باشد و به Ollama و مدل embedding نیاز دارد.

تغییر قیمت و موجودی به بازسازی embedding نیاز ندارد، چون هنگام پاسخ از SQL خوانده می‌شوند. تغییر نام یا توضیحات محصول متن دانش را عوض می‌کند و در بازسازی بعدی هش جدید و embedding تازه می‌سازد. بردارهای جست‌وجو در snapshot حافظه‌ای به‌روز می‌شوند؛ وضعیت را در `GET /api/knowledge/status` کنترل کنید.

## داده‌ها و جدول‌های اصلی

برنامه با EF Core به SQL Server وصل می‌شود. نگاشت موجودیت‌ها در `SkinRag.Api/Data/AppDbContext.cs` تعریف شده است. `CatalogService` عملیات کاتالوگ را انجام می‌دهد و `ProductRepository` پرس‌وجوهای لازم برای مشاوره و بازیابی محصول را فراهم می‌کند.

| جدول | اطلاعاتی که نگه می‌دارد |
| --- | --- |
| `Products` | نام، توضیحات، برند و دسته، اطلاعات پوست و مو، قیمت و موجودی قدیمی، وضعیت فعال و متن‌های جست‌وجو |
| `Categories` | دسته‌های اصلی و زیردسته‌ها به همراه حوزهٔ پوست، مو یا زیبایی |
| `Brands` | برند محصول |
| `Profiles` | پروفایل‌های نوع پوست و مو |
| `Concerns` | دغدغه‌ها و عبارت‌های مرتبط با جست‌وجو |
| `Ingredients` | ترکیبات و نام‌های مرتبط |
| `ProductProfiles` | ارتباط چندبه‌چند محصولات با پروفایل‌ها |
| `ProductConcerns` | ارتباط چندبه‌چند محصولات با دغدغه‌ها |
| `ProductIngredients` | ارتباط چندبه‌چند محصولات با ترکیبات |
| `ProductVariants` | گونه‌های محصول، مانند اندازه یا رنگ، همراه با قیمت، SKU و موجودی |
| `ProductEmbeddings` | بردار محصول، مدل، ابعاد، هش محتوا و زمان تولید |
| `ConsultationPerformanceLogs` | مدت اجرای درخواست‌های مشاوره و زمان هر مرحله |

در محصولی که گونه دارد، قیمت و موجودی می‌تواند برای هر گونه جدا باشد. فیلتر رنگ، اندازه، قیمت و موجودی باید با همان گونهٔ محصول سازگار باشد. برای محصولات قدیمی بدون گونه، فیلدهای خود محصول استفاده می‌شوند. دادهٔ آزمایشی را با قیمت یا مشخصات تأییدشدهٔ فروشنده اشتباه نگیرید.

## ثبت زمان پاسخ‌گویی

هر درخواستی که به `ConsultationService` برسد، یک رکورد در `ConsultationPerformanceLogs` می‌سازد. ثبت از صف پس‌زمینه انجام می‌شود تا نوشتن در دیتابیس به زمان پاسخ کاربر اضافه نشود. متن پرسش ذخیره نمی‌شود. اندازه‌گیری‌ها بر حسب میلی‌ثانیه‌اند و مرحله‌ای که در آن درخواست اجرا نشده باشد، مقدار خالی دارد.

| ستون | معنی |
| --- | --- |
| `StartedAtLocal` و `CompletedAtLocal` | زمان شروع و پایان درخواست با ساعت محلی سرور برنامه |
| `TotalMs` | زمان کل پردازش داخل سرویس مشاوره |
| `IntentMs` | مدت تشخیص نیت |
| `CatalogReadMs` | مدت خواندن واژگان و گزینه‌های کاتالوگ |
| `QueryBuildMs` | مدت ساخت برنامهٔ جست‌وجو، با احتساب استخراج مدل در صورت نیاز |
| `SearchQuery` | عبارت نهایی جست‌وجو در کاتالوگ؛ با `Telemetry:LogSearchQuery=false` می‌توان ثبت آن را خاموش کرد |
| `QuerySource` و `ModelCallsJson` | منشأ برنامهٔ جست‌وجو و جزئیات زمان‌بندی، بارگذاری و توکن‌های هر فراخوانی Ollama |
| `SqlFilterMs` | مدت اجرای فیلتر SQL برای یافتن شناسه‌های واجد شرایط |
| `EmbeddingMs` | مدت ساخت بردار پرس‌وجو با Ollama |
| `ProductLoadMs` | مدت خواندن اطلاعات محصول از SQL |
| `AnswerGenerationMs` | مدت تولید پاسخ مشاوره با مدل |
| `ValidationMs` | مدت اعتبارسنجی پیشنهادها و پاسخ |
| `Outcome` و `ErrorType` | نتیجهٔ موفق یا ناموفق و نوع خطا، در صورت وجود |
| `Intent`، `RetrievalMethod` و `ResponseMode` | مسیر انتخاب‌شده برای تحلیل، بازیابی و پاسخ |
| `ProductCount` | تعداد محصول‌های برگشتی |

برای دیدن ۱۰۰ درخواست اخیر، این دستور را در SQL Server اجرا کنید:

<div dir="ltr">

```sql
SELECT TOP (100)
    StartedAtLocal,
    CompletedAtLocal,
    TotalMs,
    IntentMs,
    CatalogReadMs,
    QueryBuildMs,
    QuerySource,
    SearchQuery,
    ModelCallsJson,
    SqlFilterMs,
    EmbeddingMs,
    ProductLoadMs,
    AnswerGenerationMs,
    ValidationMs,
    Outcome,
    ErrorType,
    RetrievalMethod,
    ResponseMode
FROM dbo.ConsultationPerformanceLogs
ORDER BY StartedAtLocal DESC;
```

</div>

اگر `AnswerGenerationMs` بزرگ باشد، زمان عمده صرف پاسخ‌سازی Ollama می‌شود. اگر `EmbeddingMs` بزرگ باشد، ساخت بردار پرس‌وجو کند است. مقدار بزرگ `CatalogReadMs` یا `SqlFilterMs` را با وضعیت SQL Server و حجم داده مقایسه کنید. برای دیدن میانگین مرحله‌ها در درخواست‌های موفق، می‌توانید این پرس‌وجو را اجرا کنید:

<div dir="ltr">

```sql
SELECT
    COUNT(*) AS RequestCount,
    AVG(CAST(TotalMs AS float)) AS AverageTotalMs,
    AVG(AnswerGenerationMs) AS AverageAnswerGenerationMs,
    AVG(EmbeddingMs) AS AverageEmbeddingMs,
    AVG(SqlFilterMs) AS AverageSqlFilterMs
FROM dbo.ConsultationPerformanceLogs
WHERE Outcome = N'success';
```

</div>

پس از دریافت تغییرات کد، API را دوباره اجرا کنید تا ثبت زمان‌ها فعال باشد. جدول باید پیش‌تر با `database/consultation-performance.sql` ساخته شده باشد؛ اگر جدول وجود نداشته باشد، سرویس پس‌زمینه خطای ذخیره‌سازی را در گزارش برنامه ثبت می‌کند.

## مسیرهای وب و <bdi dir="ltr">API</bdi>

### صفحه‌های وب

| مسیر | کارکرد |
| --- | --- |
| `/` | هدایت به صفحهٔ چت |
| `/chat` | گفت‌وگو با دستیار، انتخاب فیلترها و دیدن کارت محصول |
| `/admin` | مشاهدهٔ آمار کاتالوگ، وضعیت نمایهٔ دانش و بازسازی دستی |
| `/swagger` | مستندات تعاملی API در محیط Development |

### مسیرهای API

| روش و مسیر | کارکرد |
| --- | --- |
| `GET /api/catalog/filters` | خواندن حوزه‌ها، دسته‌ها، برندها، پروفایل‌ها، دغدغه‌ها، ترکیبات، رنگ‌ها و جلوه‌ها |
| `GET /api/catalog/stats` | خواندن آمار محصولات، محصولات فعال و موجود، گونه‌ها، دسته‌ها و برندها |
| `GET /api/catalog/products` | جست‌وجوی صفحه‌بندی‌شدهٔ کاتالوگ با فیلتر |
| `GET /api/catalog/products/{id}` | دریافت جزئیات محصول و گونه‌های فعال |
| `POST /api/consultation/ask` | دریافت مشاوره و پیشنهاد محصول |
| `GET /api/knowledge/status` | دیدن وضعیت، پیشرفت، خطا و زمان آخرین snapshot دانش |
| `POST /api/knowledge/rebuild?force=false` | بررسی و بازسازی معمول با استفاده از بردارهای cacheشدهٔ معتبر |
| `POST /api/knowledge/rebuild?force=true` | نادیده گرفتن cache و بازسازی همهٔ بردارهای محصولات فعال |
| `GET /health/live` | بررسی زنده بودن برنامه |
| `GET /health/ready` | بررسی اتصال دیتابیس و آماده بودن نمایهٔ دانش |

مسیر مشاوره برای هر نشانی IP حداکثر ۱۲ درخواست در دقیقه می‌پذیرد. اندازهٔ صفحهٔ فهرست محصولات بین ۱ تا ۱۰۰ است. پارامترهای فیلتر مهم شامل `domain`، `categorySlug`، `brandSlug`، `skinType`، `hairType`، `concernSlug`، `minPrice`، `maxPrice`، `shade`، `finish`، `sizeValue`، `sizeUnit`، `fragranceFree` و `excludeIngredientSlugs` هستند.

جست‌وجوی آزاد کاتالوگ پارامترهای `search`، `page`، `pageSize` و `inStockOnly` را می‌پذیرد. پارامتر حذف ترکیبات را می‌توان تکرار کرد. درخواست مشاوره، علاوه بر متن، می‌تواند فیلترهای کاتالوگ را به صورت JSON بفرستد:

<div dir="ltr">

```json
{
  "question": "برای موی فر یک کرم بدون آبکشی می‌خواهم",
  "domain": "hair",
  "hairType": "hair-curly",
  "categorySlug": "leave-in",
  "maxPrice": 1800000,
  "excludeIngredientSlugs": ["fragrance"]
}
```

</div>

پاسخ مشاوره فیلدهایی مانند `answer`، `products`، `currency`، `retrievalMethod`، `eligibleProducts`، `indexUpdatedAtUtc`، `isDemo` و `responseMode` دارد. اطلاعات قیمت، موجودی و کارت‌ها را از `products` بخوانید؛ `answer` متن پاسخ گفتگوست.

## تنظیمات برنامه و مدل‌ها

تنظیمات پیش‌فرض در `SkinRag.Api/appsettings.json` قرار دارند. تنظیم محیطی .NET می‌تواند هر مقدار را بازنویسی کند؛ برای نمونه، متغیر `ConnectionStrings__DefaultConnection` مقدار اتصال SQL Server را تعیین می‌کند.

| کلید | کاربرد و مقدار پیش‌فرض مهم |
| --- | --- |
| `ConnectionStrings:DefaultConnection` | رشتهٔ اتصال به SQL Server |
| `Ollama:BaseUrl` | نشانی Ollama؛ در تنظیم پیش‌فرض `http://localhost:11434` |
| `Ollama:IntentModel` | مدل تشخیص نیت؛ در تنظیم فعلی `qwen2.5:3b` |
| `Ollama:QueryModel` | مدل استخراج فیلترها؛ در تنظیم فعلی `qwen2.5:3b` |
| `Ollama:ConsultationModel` | مدل تولید پاسخ؛ در تنظیم فعلی `qwen2.5:3b` |
| `Ollama:ChatModel` | مدل پیش‌فرض جایگزین؛ در تنظیم فعلی `qwen2.5:7b` |
| `Ollama:EmbeddingModel` | مدل بردارسازی؛ در تنظیم فعلی `nomic-embed-text` |
| `Ollama:RequestTimeoutSeconds` | مهلت HTTP کلی برای Ollama؛ پیش‌فرض ۳۰۰ ثانیه |
| `Ollama:ContextWindow` | اندازهٔ زمینهٔ مدل؛ پیش‌فرض ۲۰۴۸ توکن |
| `Consultation:TimeoutSeconds` | مهلت کل درخواست مشاوره؛ پیش‌فرض ۲۲۰ ثانیه |
| `Consultation:IntentTimeoutSeconds` | حداکثر انتظار تشخیص نیت؛ پیش‌فرض ۷۰ ثانیه |
| `Consultation:QueryTimeoutSeconds` | حداکثر انتظار استخراج query؛ پیش‌فرض ۶۰ ثانیه |
| `Consultation:AnswerTimeoutSeconds` | حداکثر انتظار تولید پاسخ؛ پیش‌فرض ۶۰ ثانیه |
| `Rag:TopK` | تعداد نامزدهای نهایی بازیابی؛ پیش‌فرض ۵ |
| `Rag:MinimumSimilarity` | حداقل شباهت برداری برای نگه‌داشتن نامزد؛ پیش‌فرض ۰٫۲ |
| `Rag:EmbeddingBatchSize` | تعداد محصول‌های هر دستهٔ embedding؛ پیش‌فرض ۱۶ |
| `Rag:DocumentPrefix` و `Rag:QueryPrefix` | پیشوند متن محصول و عبارت جست‌وجو برای embedding |
| `Rag:EmbeddingVersion` | نسخهٔ منطق محتوای بردارها برای تشخیص cache معتبر |
| `Rag:RefreshIntervalSeconds` | فاصلهٔ بررسی دوره‌ای snapshot؛ پیش‌فرض ۳۰۰ ثانیه |

مدل embedding و مدل گفتگو وظایف متفاوت دارند. تغییر مدل پاسخ در `Ollama:ConsultationModel` روی زمان و کیفیت متن پاسخ اثر می‌گذارد؛ تغییر آن به مدل کوچک‌تر معمولاً منابع کمتری مصرف می‌کند، اما باید کیفیت فارسی و دقت پاسخ را با پرسش‌های واقعی بررسی کرد. تغییر مدل embedding با نام یا نسخهٔ متفاوت، مستلزم بازسازی بردارهای محصولات است.

## رابط کاربری

صفحه‌های `/chat` و `/admin` در `Views/Pages/` هستند و `PagesController` آن‌ها را ارائه می‌کند. قالب کلی صفحه در `Views/Shared/_Layout.cshtml` قرار دارد. فایل `wwwroot/assets/chat.js` درخواست مشاوره را می‌فرستد و پاسخ را به پیام و کارت‌های محصول تبدیل می‌کند؛ `admin.js` وضعیت کاتالوگ و بازسازی نمایه را مدیریت می‌کند. فایل `app.css` چیدمان و رنگ‌های مشترک را تعریف می‌کند. قلم و منابع رابط در خود پروژه‌اند و برای نمایش صفحات به CDN وابسته نیستند.

## ساخت، اجرا و عیب‌یابی

برای ساخت راهکار از پوشهٔ اصلی مخزن اجرا کنید:

<div dir="ltr">

```powershell
dotnet build SkinRag.sln
```

</div>

برای اجرای بررسی‌های مستقل منطق، بدون نیاز به سرویس زندهٔ دیتابیس یا Ollama:

<div dir="ltr">

```powershell
dotnet run --project tests/SkinRag.Checks
```

</div>

| نشانه | مواردی که باید بررسی شوند |
| --- | --- |
| چت اعلام می‌کند دانش آماده نیست | اتصال SQL Server، محصولات فعال، اجرای Ollama و وضعیت `GET /api/knowledge/status` را بررسی کنید |
| بازسازی دانش خطا می‌دهد | گزارش اجرای API، اتصال SQL، مدل embedding و دسترسی Ollama را بررسی کنید |
| مشاوره کند است | ستون‌های `AnswerGenerationMs`، `EmbeddingMs` و `QueryBuildMs` در جدول زمان‌سنجی نشان می‌دهند کدام مرحله کند است |
| مدل در دسترس نیست | اجرای Ollama، مقدار `Ollama:BaseUrl` و نصب مدل‌های تنظیم‌شده را کنترل کنید |
| قیمت یا موجودی نادرست به نظر می‌رسد | اطلاعات محصول و گونه‌های فعال را در SQL Server بررسی کنید؛ این دو مقدار هنگام درخواست از دیتابیس خوانده می‌شوند |
| Swagger دیده نمی‌شود | مطمئن شوید برنامه در محیط Development اجرا شده است |

گزارش‌های برنامه نیز در همان ترمینال اجرای `dotnet run` یا پنجرهٔ خروجی محیط توسعه دیده می‌شوند. خطاهای API با `traceId` ثبت می‌شوند تا درخواست ناموفق را در گزارش‌ها پیدا کنید.

</div>
