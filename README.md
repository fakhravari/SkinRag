# SkinRag؛ کاتالوگ و مشاور محصولات پوست، مو و زیبایی

SkinRag یک برنامهٔ وب با **ASP.NET Core و .NET 8** است. اطلاعات کاتالوگ و بردارهای جست‌وجو در **SQL Server** نگه‌داری می‌شوند و مدل‌های زبانی و بردارسازی از طریق **Ollama** در دسترس برنامه‌اند. رابط کاربر و پنل مدیریت با **Razor، JavaScript و CSS** ساخته شده‌اند.

## معماری در یک نگاه

پروژه یک برنامهٔ ASP.NET Core است که کد آن بر اساس مسئولیت در پوشه‌ها گروه‌بندی شده است. این پوشه‌ها مرز مفهومی ایجاد می‌کنند؛ هرکدام پروژهٔ جداگانهٔ .NET نیستند.

### مرز وابستگی‌ها

کنترلرها لایهٔ HTTP هستند و باید تا حد ممکن سبک بمانند. منطق مکالمه در `ConsultationService`، منطق جست‌وجو در `QueryBuilder` و `ProductRetriever`، و ارتباط با SQL و Ollama در پیاده‌سازی‌های زیرساختی قرار دارد. قراردادهای `IProductRepository` و `IOllamaClient` محل اتصال منطق برنامه به این پیاده‌سازی‌ها هستند؛ نگاشت وابستگی‌ها در `Hosting/ServiceCollectionExtensions.cs` انجام می‌شود.

`CatalogService` عملیات کاتالوگ را با EF Core انجام می‌دهد و `ProductRepository` مسیرهای جست‌وجوی مورد استفاده در مشاوره را فراهم می‌کند. هر دو در همین برنامه به `AppDbContext` دسترسی دارند؛ تفکیک آن‌ها بر پایهٔ نوع عملیات کاتالوگ و مشاوره است، نه جداسازی به سرویس‌های مستقل.

## جریان درخواست مشاوره و جست‌وجوی محصول

۱. صفحهٔ `/chat` پرسش و فیلترهای انتخاب‌شده را به `POST /api/consultation/ask` می‌فرستد.

۲. `ConsultationController` ورودی HTTP را به `ConsultationService` می‌سپارد. طول پیام، متن و ورودی‌های نامعتبر در این مرحله بررسی می‌شوند.

۳. `IntentClassifier` تشخیص می‌دهد پیام احوال‌پرسی، جست‌وجوی محصول، درخواست جزئیات، قیمت، مقایسه یا پیگیری گفت‌وگوی قبلی است. قواعد قطعی و مدل intent در تشخیص سهم دارند.

۴. `QueryBuilder` پیام را به `SearchPlan` تبدیل می‌کند: متن مناسب بازیابی، حوزهٔ پوست/مو/آرایش، فیلترهای کاتالوگ، سقف بودجه و ارجاع معتبر به گفت‌وگوی قبلی.

۵. `ProductRetriever` ابتدا محصولات مجاز را با فیلترهای SQL محدود می‌کند. سپس متن پرسش را با پیشوند `QueryPrefix` به بردار تبدیل کرده و شباهت معنایی را با بردارهای محصولات می‌سنجد. رتبه‌بندی ترکیبی از **۸۰٪ شباهت برداری** و **۲۰٪ هم‌پوشانی واژه‌ها** است. مقدار `MinimumSimilarity` نتیجه‌های کم‌شباهت را کنار می‌گذارد و `TopK` حداکثر نامزدهای بازیابی را تعیین می‌کند.

۶. برای پیشنهاد معمول، حداکثر دو نامزد به مدل پاسخ‌گو داده می‌شود. `RecommendationValidator` شناسه و دلیل پیشنهاد را با محصولات مجاز مقایسه می‌کند و مشخصات جاری را دوباره از SQL می‌خواند. مدل نمی‌تواند محصول خارج از نامزدهای بازیابی را به‌عنوان پیشنهاد معتبر وارد پاسخ کند.

۷. پاسخ JSON از API شامل متن، محصولات و اطلاعات بازیابی است. رابط چت کارت محصول را از دادهٔ ساختاریافته می‌سازد؛ نام، کد، دسته، قیمت و موجودی در کارت نمایش داده می‌شوند و ترکیبات، هشدارها و راهنمای مصرف در جزئیات کارت قرار دارند.

در درخواست قیمت، موجودی، جزئیات و مقایسه، محصولات هم از SQL دوباره خوانده می‌شوند. قیمت و موجودی برای هر درخواست از دیتابیس می‌آیند و به تازه‌سازی embedding وابسته نیستند.

## جریان ساخت و به‌روزرسانی دانش RAG

۱. `KnowledgeIndexWorker` هنگام شروع برنامه و سپس در بازهٔ `Rag:RefreshIntervalSeconds` محصولات فعال را برای ساخت snapshot بررسی می‌کند.

۲. `KnowledgeIndexService` برای هر محصول یک متن دانشی از نام، دسته، برند، پروفایل‌ها، دغدغه‌ها، کلیدواژه‌ها، ترکیبات، توضیحات، هشدارها و تنوع‌های فعال می‌سازد.

۳. متن‌ها با `DocumentPrefix` و مدل `Ollama:EmbeddingModel` به‌صورت batch بردارسازی می‌شوند. بردار، نام مدل، ابعاد، هش محتوا و زمان تولید در جدول `ProductEmbeddings` نگه‌داری می‌شوند.

۴. هش هر محصول از نسخهٔ کاتالوگ، پیشوند سند و متن نهایی محصول ساخته می‌شود. در بازسازی عادی، هش برابر یعنی بردار از کش خوانده می‌شود؛ تغییر متن یا نسخه باعث تولید دوبارهٔ بردار همان محصول خواهد شد.

۵. دکمهٔ بازسازی ادمین با تیک خاموش، محصولات را بررسی و کش معتبر را استفاده می‌کند. با تیک «تولید دوبارهٔ تمام بردارها»، کش نادیده گرفته می‌شود و همهٔ محصولات فعال دوباره بردارسازی می‌شوند. این کار مقدار `EmbeddingVersion` در تنظیمات را عوض نمی‌کند.

۶. بازسازی ناموفق snapshot قبلی را نگه می‌دارد. بازسازی دستی و خودکار از یک سرویس استفاده می‌کنند و به‌صورت ترتیبی اجرا می‌شوند. فیلترهای بازیابی روی محصولات فعال و موجود اعمال می‌شوند؛ قیمت و موجودی تازه هنگام پاسخ از SQL خوانده می‌شوند.

`EmbeddingVersion` یک نشانه برای بی‌اعتبارکردن کش بردارهای کاتالوگ است، نه شمارهٔ هر بار اجرای بازسازی. آن را زمانی افزایش دهید که روش تولید متن محصول، پیشوند سند، یا نسخهٔ وزن‌های embedding با همان نام تغییر کرده باشد. اگر فقط اطلاعات یک محصول تغییر کند، هش محتوا همان محصول را برای بردارسازی دوباره مشخص می‌کند.

## مدل‌ها و تنظیمات

تنظیم‌های پیش‌فرض در `SkinRag.Api/appsettings.json` هستند. متغیرهای محیطی .NET می‌توانند آن‌ها را بازنویسی کنند؛ برای نمونه `ConnectionStrings__DefaultConnection`.

| کلید | کاربرد |
| --- | --- |
| `Ollama:BaseUrl` | نشانی سرویس Ollama |
| `Ollama:ChatModel` | مدل پیش‌فرض گفت‌وگو؛ در تنظیم فعلی `qwen2.5:7b` |
| `Ollama:ConsultationModel` | مدل ساخت پاسخ مشاوره |
| `Ollama:IntentModel` | مدل کمکی تشخیص نیت |
| `Ollama:QueryModel` | مدل کمکی استخراج فیلترها و query |
| `Ollama:EmbeddingModel` | مدل بردارسازی؛ در تنظیم فعلی `nomic-embed-text` |
| `Consultation:*` | زمان انتظار و سقف توکن مراحل intent، query و پاسخ |
| `Rag:TopK` | حداکثر نامزدهای بازیابی پیش از محدودیت پیشنهاد نهایی |
| `Rag:MinimumSimilarity` | حداقل شباهت برداری برای پذیرش نامزد |
| `Rag:EmbeddingBatchSize` | اندازهٔ دستهٔ تولید بردار |
| `Rag:DocumentPrefix` | پیشوند متن سند/محصول در زمان ایندکس |
| `Rag:QueryPrefix` | پیشوند متن پرسش در زمان جست‌وجو |
| `Rag:EmbeddingVersion` | نسخهٔ هش کش بردارهای کاتالوگ؛ فعلاً `catalog-v4` |
| `Rag:RefreshIntervalSeconds` | فاصلهٔ بررسی پس‌زمینه؛ فعلاً ۳۰۰ ثانیه |

مدل گفت‌وگو و مدل embedding دو وظیفهٔ جدا دارند. `nomic-embed-text` برای تولید بردار و جست‌وجوی معنایی استفاده می‌شود؛ متن پاسخ را مدل chat می‌سازد.

## ساختار داده

| جدول | کاربرد |
| --- | --- |
| `Products` | مشخصات پایه و فیلدهای متنی سازگار با داده‌های قدیمی |
| `Categories` و `Brands` | دسته، حوزه و برند محصول |
| `Profiles` و `ProductProfiles` | پروفایل نوع پوست/مو و ارتباط محصول با آن |
| `Concerns` و `ProductConcerns` | دغدغه‌ها و اصطلاحات جست‌وجوی مرتبط |
| `Ingredients` و `ProductIngredients` | ترکیبات فارسی/INCI و فیلتر حذف ترکیب |
| `ProductVariants` | SKU، اندازه، رنگ، جلوه، قیمت و موجودی هر تنوع |
| `ProductEmbeddings` | بردار، مدل، ابعاد، هش محتوا و زمان ایندکس |

در محصول‌های دارای تنوع، قیمت و موجودی تنوع‌ها مرجع نمایش و فیلتر است. هر شرط رنگ، اندازه، بازهٔ قیمت و موجودی باید برای همان یک تنوع برقرار باشد. در محصول قدیمی فاقد تنوع، فیلدهای اصلی محصول استفاده می‌شوند.

داده‌های نمونه برای ارزیابی فنی و ساختگی‌اند. اگر `IsDemo` فعال باشد، کارت محصول اعلام می‌کند که قیمت و مشخصات آن هنوز با فروشنده تأیید نشده‌اند. نبود اطلاعات یک ترکیب به معنی تضمین ایمنی محصول برای حساسیت نیست.

## مسیرهای HTTP

| روش و مسیر | کاربرد |
| --- | --- |
| `GET /api/catalog/filters` | فهرست دسته، برند، پروفایل، دغدغه، ترکیب، رنگ و جلوهٔ معتبر |
| `GET /api/catalog/stats` | آمار محصولات، تنوع‌ها و دسته‌ها |
| `GET /api/catalog/products` | فهرست صفحه‌بندی‌شده با جست‌وجو و فیلتر |
| `GET /api/catalog/products/{id}` | جزئیات محصول و تنوع‌های فعال |
| `POST /api/consultation/ask` | دریافت مشاوره و پیشنهاد محصول |
| `GET /api/knowledge/status` | آمادگی، پیشرفت و وضعیت snapshot دانش |
| `POST /api/knowledge/rebuild?force=false` | بررسی/بازسازی کاتالوگ؛ `force=true` کش را نادیده می‌گیرد |
| `GET /health/live` | بررسی زنده‌بودن برنامه |
| `GET /health/ready` | بررسی اتصال SQL و آمادگی دانش؛ تا آماده‌شدن پاسخ ۵۰۳ می‌دهد |

بازسازی دستی از پنل ادمین بدون کلید مدیریتی و بدون محدودیت نرخ جداگانه در دسترس است. عملیات هم‌زمان از یک سرویس مشترک عبور می‌کنند و به‌ترتیب اجرا می‌شوند. مسیر مشاوره برای هر IP محدودیت نرخ دارد.

فیلترهای مشترک کاتالوگ شامل `domain`، `categorySlug`، `brandSlug`، `skinType`، `hairType`، `concernSlug`، `minPrice`، `maxPrice`، `shade`، `finish`، `sizeValue`، `sizeUnit`، `fragranceFree` و `excludeIngredientSlugs` هستند. `categorySlug` یک دستهٔ اصلی، زیردسته‌هایش را هم در بر می‌گیرد. در جست‌وجوی آزاد، دغدغه متن‌محور است؛ `concernSlug` فیلتر قطعی دیتابیس است.

پارامترهای فهرست محصولات `search`، `page`، `pageSize` و `inStockOnly` هستند. جست‌وجوی متنی نام محصول، کلیدواژه یا SKU را بررسی می‌کند. حداکثر `pageSize` برابر ۱۰۰ است. برای آرایهٔ حذف ترکیبات در GET، پارامتر را تکرار کنید؛ مانند `excludeIngredientSlugs=fragrance&excludeIngredientSlugs=shea`.

نمونهٔ درخواست مشاوره:

<div dir="ltr">

```json
{
  "question": "برای موی فر و وز یک کرم مو بدون آبکشی می‌خواهم",
  "domain": "hair",
  "hairType": "hair-curly",
  "categorySlug": "leave-in",
  "maxPrice": 1800000,
  "excludeIngredientSlugs": ["fragrance"]
```

پاسخ مشاوره فیلدهایی مانند `answer`، `products`، `currency`، `retrievalMethod`، `eligibleProducts`، `indexUpdatedAtUtc`، `isDemo` و `responseMode` دارد. هر محصول شامل دادهٔ ساختاریافتهٔ محصول، شباهت و امتیاز بازیابی است. قیمت، موجودی و مشخصات کارت را از `products` بخوانید؛ `answer` متن مکالمه است.

## صفحه‌های وب

| مسیر | مسئولیت |
| --- | --- |
| `/chat` | گفت‌وگو با دستیار، انتخاب حوزه و فیلتر، نمایش کارت محصول و گفت‌وگوی جدید |
| `/admin` | آمار کاتالوگ، اتصال دیتابیس، مدل‌ها، وضعیت/پیشرفت ایندکس و بازسازی دستی |
| `/` | هدایت به `/chat` |

صفحه‌ها در `Views/Pages/` قرار دارند و `Controllers/PagesController.cs` آن‌ها را ارائه می‌کند. قالب مشترک، ناوبری و فایل‌های عمومی در `Views/Shared/_Layout.cshtml` هستند. نسخهٔ فایل‌های CSS و JavaScript با Tag Helper بر اساس محتوای فایل به مرورگر معرفی می‌شود.

کد رابط چت در `wwwroot/assets/chat.js` درخواست را می‌سازد و پاسخ را به متن و کارت‌های امن تبدیل می‌کند؛ دادهٔ سرور به‌صورت text نمایش داده می‌شود و HTML اجرایی تلقی نمی‌شود. `admin.js` وضعیت پایگاه دانش و آمار ادمین را می‌خواند و عملیات بازسازی را مدیریت می‌کند. `app.css` توکن‌های رنگ و چیدمان مشترک را تعریف می‌کند. فونت Vazirmatn و منابع رابط در خود پروژه قرار دارند؛ برای نمایش صفحه‌ها CDN لازم نیست.

## راه‌اندازی توسعه

نیازمندی‌ها: .NET SDK سازگار با .NET 8، SQL Server و Ollama. ابزار `sqlcmd` برای نصب/بررسی پایگاه داده و Python برای اسکریپت‌های seed یا smoke test لازم است؛ اجرای API به Python وابسته نیست.

۱. رشتهٔ اتصال را در `SkinRag.Api/appsettings.json` یا متغیر محیطی `ConnectionStrings__DefaultConnection` تنظیم کنید.

۲. برنامه باید به پایگاه داده‌ای با schema سازگار وصل شود. در نسخهٔ فعلی مخزن، فایل پشتیبان `database/SkinRagDb.bak` موجود است، اما اسکریپت نصب، ارتقا یا seed همراه سورس نیست. برای آماده‌سازی دیتابیس، از نسخهٔ معتبر و روند مدیریت دیتابیس محیط خود استفاده کنید.

۳. مدل‌های مورد استفاده را در Ollama آماده کنید:

<div dir="ltr">

```powershell
ollama pull nomic-embed-text
ollama pull qwen2.5:7b
ollama pull qwen2.5:3b
```

</div>

۴. برنامه را اجرا کنید:


</div>

Swagger در محیط Development از `/swagger` قابل‌دسترسی است. تنظیمات محلی اجرای برنامه در `SkinRag.Api/Properties/launchSettings.json` قرار دارند.

## بررسی و ابزارهای داده

ساخت کل راهکار:

<div dir="ltr">

```powershell
dotnet build SkinRag.sln --no-restore
```

</div>

بررسی‌های مستقل منطق بدون دیتابیس و Ollama:

<div dir="ltr">

```powershell
dotnet run --project tests/SkinRag.Checks
```

</div>

برای smoke test، ابتدا API را اجرا کنید:

<div dir="ltr">

```powershell
python scripts/smoke_test.py
python scripts/smoke_test.py --chat
```

</div>

گزینهٔ `--chat` درخواست واقعی به Ollama می‌فرستد و به مدل و آماده‌شدن ایندکس نیاز دارد. smoke test کاتالوگ هم انتظار دارد دیتابیس حاوی دادهٔ سازگار آزمایشی باشد. فایل `scripts/smoke_test.py` گزینهٔ `--base-url` برای نشانی متفاوت API دارد.
